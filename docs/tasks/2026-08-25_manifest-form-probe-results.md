## Контроль фикстуры (AK5)

Встроенная синтетическая фикстура прогоняется ПЕРВОЙ, через ТЕ ЖЕ
функции, что и боевой прогон (`classify_z1`, `z2_missing_for_dispatch`,
`classify_z3_form`, `link_dispatch_outcome`). Позитивный прогон:

```
z1: факт={'section': 1, 'prose_only': 1, 'none': 1}
z1: ожидание={'section': 1, 'prose_only': 1, 'none': 1}
z2: факт={'INLINE': 2, 'POINTER': 2, 'OTHER': 0, 'total_missing': 4}
z2: ожидание={'INLINE': 2, 'POINTER': 2, 'OTHER': 0, 'total_missing': 4}
z3: факт={'pointer_form': 2, 'inline_form': 1, 'no_given_declaration': 1, 'linked': 2, 'unknown': 1, 'rejected': 1, 'accepted': 1}
z3: ожидание={'pointer_form': 2, 'inline_form': 1, 'no_given_declaration': 1, 'linked': 2, 'unknown': 1, 'rejected': 1, 'accepted': 1}
фикстура сошлась с ожиданием (дефектов нет)
```

Негативный контроль (`--negative-control`, ожидание z1.section
сознательно сдвинуто 1→2) -- дословный вывод:

```
=== КОНТРОЛЬ ФИКСТУРЫ (НЕГАТИВНЫЙ КОНТРОЛЬ, ожидание СОЗНАТЕЛЬНО сдвинуто z1.section 1->2) ===
  z1: факт={'section': 1, 'prose_only': 1, 'none': 1}
  z1: ожидание={'section': 2, 'prose_only': 1, 'none': 1}
  ...
  ДЕФЕКТ ИНСТРУМЕНТА: фикстура не сошлась с ожиданием:
    - z1.section: ожидание 2, факт 1
НЕГАТИВНЫЙ КОНТРОЛЬ ПОДТВЕРЖДЁН: расхождение найдено, как и ожидалось -- контроль не декоративен.
```
Exit code негативного контроля: 1 (правильно).

По пути фикстура ПОЙМАЛА два реальных бага реализации (не декоративна
на практике, а не только по конструкции): (1) метка `given` внутри
собственного описания фикстуры ложно давала совпадение
`MANIFEST_GIVEN_RE` там, где его не должно было быть; (2) счёт
путь-токенов для З3 по ВСЕМУ промпту (а не только внутри секции
`given`) искажался путём из секции `owns` того же диспатча. Оба
исправлены до боевого прогона.

## Чего этот замер не показывает (AK7, обязательный раздел)

1. **Слепота субагентского потока.** В ЭТОМ корпусе она измерена как
   0 (не нашлось ни одного Task/Agent-вызова внутри `subagents/*.jsonl`
   в принципе) -- но это СВОЙСТВО ДАННЫХ на момент замера (совпадает с
   политикой flat delegation), не гарантия механизма: если когда-то
   появится вложенный диспатч из воркера, он останется НЕВИДИМ этому
   замеру точно так же, как warn_density's Ф1-находка про hook_success.
2. **Доля несвязанных диспатчей в З3.** unknown = 1/28 (окно #8),
   4/74 (сводно) -- это не ноль; каждый unknown исключён из
   rejected/accepted знаменателя, но включён в общий "given-декл."
   счёт. Причина unknown не диагностирована поштучно (могло быть:
   диспатч заблокирован гейтом до спавна субагента -- тогда meta.json
   физически не может существовать; либо диспатч не залогирован в
   журнал вовсе).
3. **Эвристичность классификатора З2.** Решающее дерево
   (read-verb → POINTER; вне секции → POINTER; ≥2 токена в секции →
   INLINE; единственный → POINTER; иначе → OTHER) судит по ФОРМЕ
   строки (регексы), не по смыслу. Токен, который человек прочтёт как
   "цель ссылки" в предложении без формальных read-глаголов спеки,
   может уйти в OTHER или в INLINE, если рядом случайно оказался ещё
   один путь-токен той же секции манифеста (например, owns-путь,
   если секция given не закрылась до него -- см. следующий пункт).
4. **У секции `given` (в отличие от `owns`) НЕТ верхней границы в
   `_section_map()` живого гейта** (D-3 сузила ТОЛЬКО owns-секцию,
   не given -- см. докстринг `tools/dispatch_gate.py` :1390-1404).
   Значит "секция given" в этом замере тянется от заголовка ДО
   следующего заголовка манифеста (owns/non-goals/handoff), включая
   пустые строки и обычную прозу между путями -- это ЖИВОЕ поведение
   гейта, не баг замера, но означает, что "N путь-токенов в секции
   given" иногда шире, чем читатель интуитивно ожидал бы от слова
   "секция".
5. **Расхождение 12 vs 27 в З2** не объяснено эмпирически (только
   гипотеза про региональный/bare путь гейта) -- спека прямо запретила
   подгонку, гипотеза НЕ проверялась прогоном самого `given_path_warn()`
   на тех же промптах (это отдельная, не заказанная работа).
6. **repo_root = REPO_ROOT для ВСЕХ диспатчей** (Р-2) -- если среди
   исторических диспатчей встречались обращения к ДРУГОМУ дереву
   (другой деплой, другой `cwd`), их существование путей проверялось
   бы НЕВЕРНО (относительно этого репо, а не их настоящего `cwd`).
   Не проверялось отдельно, сколько диспатчей это могло задеть.
7. **"Пишущий диспатч" (Р-1) взят как `subagent_type=='builder' И
   is_write`.** Диспатч с ДРУГИМ subagent_type, который тем не менее
   пишет файлы (например, критик, правящий вердикт в файл), в
   популяцию З1/З3 не входит -- это осознанное сужение (совпадает с
   тем, что реально требует гейт), но НЕ "все пишущие диспатчи репо" в
   бытовом смысле слова.
8. **"Два предшествующих окна" (Р-3)** взяты по ПОРЯДКУ ЗАПИСИ в
   сайдкаре, а не по хронологии границ (границы этих окон местами
   ПЕРЕКРЫВАЮТ окно №8, а не предшествуют ему по времени) -- другое
   прочтение слова "предшествующих" дало бы другие два окна или ни
   одного (сайдкар не содержит непрерывного ряда неперекрывающихся
   окон).
