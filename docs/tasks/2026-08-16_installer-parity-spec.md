# Спека механизма INSTALLER-PARITY — собрана Lead из двух принятых драфтов (t-463/t-464, 08-16)

Статус: СОБРАНА, ждёт критик-на-план (R3) → затем очередь релизного
батча (D-0074: правки toolkit/ — только релизным батчем по слову).
База — драфт t-464 (структура K1-K14); привиты усиления t-463.
Развилки обоих драфтов РЕШЕНЫ Lead ниже (§Р). Полные тексты драфтов —
журнал t-463/t-464 (вывод агентов в приёмочных notes и DAG B8).

## Что делает механизм

После установки/апгрейда кита у хоста МАШИНА сверяет, что каждое
правило И КЛАУЗА поставленной политики физически присутствует в
дереве хоста (после host-restoration), и предъявляет список
недовезённого; апгрейд получает письменный протокол слияния
CLAUDE.md, при котором restoration не может стереть новый политблок.
Класс: недовоз ec4e6f0 у Dog (файлы доехали, ~14 блоков политики —
нет; чеки-сторожа доехали и смотрели в пустоту).

## Решения развилок (Lead, 08-16) — §Р

- (а)=2: сверка ЯКОРЯМИ по политическим носителям (CLAUDE.md,
  .claude/agents/*.md, PROCESS/*.md) + присутствие остальных путей
  против леджера. Не пофайлово-хешево: замер A1 — 29 DIFF, 28
  законных на 1 настоящий, Rule #1 такой шум не переживёт.
- (б)=4: якорь на правило И на именованную клаузу (недовоз Dog жил
  клаузой внутри существующего правила — файл/блок/правило слепы).
- (в)=3: автовывод якорей из структуры (--emit-anchors: заголовки,
  номера правил, CAPS-маркеры) + extra_anchors руками; двойной
  инвариант K3 (поставленное ⊆ носитель; производное ⊆ поставленное).
- (г)=2: у хоста — WARN на установке, BLOCK на апгрейде (протоколом
  шага, НЕ хуком коммита; свидетельство класса есть именно на
  апгрейде — D-0090 лестница по evidence).
- (д)=2 + фикс: канал в toolkit/tools/wiring_check.py (WARN «ревизия
  в леджере есть, записи parity на неё нет»), fail-open; ТЕМ ЖЕ
  диспатчем чинится найденный t-464 пред-существующий баг поиска
  леджера (только корень против docs/ онбординга — вживую у Dog;
  порядок поиска K7 обязателен и печатается в шапке).
- (е)=1: инструмент read-only по дереву хоста; запись «Install
  parity: ...» пишет шаг апгрейда, не инструмент (иначе
  самосертификация в миниатюре; read-only безопасен на чужом дереве).
- (ж): протокол слияния — в Upgrade mode онбординга (семь шагов
  t-464 §1.3, вкл. карвинг-аут «restoration НИКОГДА для файла
  политики — только слияние» и парную инструкцию «манифест якорей
  заменяется целиком / CLAUDE.md целиком не заменяется никогда»);
  двухстрочные указатели — в PATCH_PROTOCOL.md ОБЕИХ копий (ось 4)
  и в INSTALL.md.
- (з)=1 + штабная нога: инструмент kit-only (штаб кит себе не
  ставит; пометка «kit-only» в оси 7 обязательна, иначе чек 12
  прочтёт как недопоставку); НО прививка t-463 S8 принимается —
  штабной чек 32 получает ногу (д) «КОНТЕНТ доехал, не только строки
  леджера: parity-прогон на дереве цели по каждому порт-батчу окна»
  (правка штабного протокола — Lead-коммит при посадке); плюс
  прививка t-463 (н): шаг «новая клауза политики → новый якорь» в
  kit-release SKILL (кухня, Lead-ход тем же батчем).
- (и)=1: один builder-диспатч на код+доки (контракт описан в четырёх
  .md и одном .py — раздельность приглашает дрейф); критик-гейт
  обязателен (>100 строк, механизм).
- (к)=1: UNKNOWN (нет строки леджера/нераспознанный статус/нет
  леджера) = exit 1, отдельная секция; bootstrap-режим края 8
  смягчает доверсионные хосты. Молчаливое «сойдёт» и было классом.

## Нормативное ядро (принятые критерии t-464, сжатая форма)

K1 инструмент toolkit/tools/install_parity.py, CLI --check /
--emit-anchors / --root / --manifest (дефолт — сосед скрипта) /
--ledger; exit 0 чисто / 1 MISSING-UNKNOWN / 2 прогону нельзя
доверять; ни одного трейсбека наружу. K2 манифест
install_parity_anchors.json ({unit_id, kit_path, host_path,
anchors[], kind}); дубли = exit 2. K3 два теста антипротухания
(обязательная половина механизма — урок F-E). K4 красный прогон:
(а) синтетика, (б) РЕГРЕССИОННЫЙ исторический — материализованный
git show ec4e6f0:CLAUDE.md обязан дать exit 1 со всеми пятью
пунктами OUTBOUND §1 поимённо (главный критерий). K5 зелёный прогон
на живом Dog (ТОЛЬКО чтение; MISSING там = находка Lead'у, не фикс).
K6 классификация отсутствующего пути по статусу леджера (adopt →
MISSING; native-equivalent/deferred/rejected → informational; иначе
UNKNOWN). K7 порядок поиска леджера: --ledger → корень → docs/;
найденный путь печатается всегда. K8 INSTALL.md: оба пути
завершаются parity-прогоном; проверка НЕ в pre-commit (иначе первый
коммит свежей установки незакрываем — инвариант края 19). K9
Upgrade mode: протокол слияния + parity как закрывающий шаг (коммит
апгрейда не ложится, пока каждый MISSING/UNKNOWN не получил решение
леджера) + случай Path A. K10 строки шаблона леджера + секция
Parity waivers (unit_id | anchor | host_path | host_equivalent
file:line | reason; waiver без host_equivalent и reason — не
waiver). K11 кит-чек 22(d). K12 канал wiring_check (по (д)=2).
K13 адверсариальная батарея t-464 §1.6 целиком (размер/вложенность/
кодировки/битое/`..`-пути/симлинки). K14 обе обвязки зелёные + оба
реальных прогона (K4b/K5) дословно в witness.

Края: полный список t-464 §1.5 принят как нормативный (лимиты с
тестами на границе и за ней; пустые/битые входы; CRLF/BOM/UTF-16;
исключение model: из парити роль-файлов — край 15; темпоральный 16
с обоими мирами; позиционные инварианты 18-19; конфликтные пары
20-24 с решениями). DoD-прогон: пять команд t-464 §1.4 + doc-witness
ключи (EN-строки фиксирует Lead при отправке диспатча — R11 (i),
решение развилки (м) драфта t-461).
