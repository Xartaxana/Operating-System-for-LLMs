# Петля самоэволюции обвязки — ежедневный протокол

Стоячая авторизация: слово оператора 2026-08-27 («запускать петлю
каждый день, чтобы она разбирала всю работу Lead, искала возможности
улучшения и сама улучшала продукт; раз в неделю — калибровка и
релиз»). Вызов итерации по расписанию или словом «запускай петлю» =
авторизация работы итерации (снимает STOP Boot Report, как next-task).

## Отличие от калибровки (граница, слово оператора)

Петля — ЕЖЕДНЕВНЫЙ ход улучшения: окно — с прошлой итерации.
Калибровка — независимый еженедельный АУДИТ по чек-листу протокола;
она проверяет И РАБОТУ ПЕТЛИ (итерации окна — материал разбора
`calibrated`). Петля НЕ закрывает чеки калибровки, НЕ пишет
`calibrated`, НЕ заменяет релиз. Релиз — еженедельно, порт-очередь
копится между релизами (решение оператора 08-27).

## Итерация: шесть этапов

1. СБОР (детерминированные скрипты, R8(f)): warn_density,
   corpus_growth --check, wiring_check, spend_report, срез журнала
   окна — ВКЛЮЧАЯ счёт rejected/defect_found по failure_class (фикс
   итерации 1). Дословный дайджест → DAG итерации.
2. ДИАГНОЗ (scout): рецидивы классов (≥2 экземпляра или экземпляр +
   известная история); одиночки отсеиваются явно. Нет рецидивов —
   итерация завершается отчётом «пусто» (нулевая итерация легальна
   и дёшева; драфты не заводятся ради числа).
3. ДРАФТ (designer, потолок 3 кандидата/итерацию): спека-кандидат в
   форме четырёх вопросов R10, развилки списком.
4. ГЕЙТ (critic, независимый контекст): факты по носителям, детектор
   реален (R10(в)), Rule #1 — цена содержания против цены класса.
5. ПОСАДКА (Lead-сессия петли): прошедшие гейт кандидаты САЖАЮТСЯ
   АВТОНОМНО — builder-диспатчи, приёмка по witness, механизменные
   коммиты с осевым блоком (mechanism_gate). ВВЕРХ К ОПЕРАТОРУ (не
   сажать, копить в CURRENT_CONTEXT «к оператору»): (а) R11a-класс —
   интерпретация намерения, выбор формы результата; (б)
   зарезервированное словом оператора — мораторий D-0074/релизы,
   цели и параметры САМОЙ петли, помеченные её словом пороги; (в)
   отмена/суперсид прежнего решения оператора. Развилка «чьё это
   решение» трактуется консервативно: сомнение = к оператору.
6. ЗАМЕР: каждый посаженный механизм несёт предсказание (какой класс
   должен перестать рецидивировать); следующие итерации меряют.
   Метрики: рецидив класса за K=3 окна (главная); сторожевые —
   warn_density по слоям, канон, boot-бюджет, spend; A/B/C-экзамен
   (DEPLOYMENT_ECONOMY_EXAM) — по ТРИГГЕРУ: ~5 посаженных механизмов
   с прошлого прогона / тронута роль/промт / релиз / слово.
   Ретирование: детектор молчит K окон И класс не рецидивирует →
   кандидат norm_retire; класс рецидивирует НЕСМОТРЯ на механизм →
   находка «сторож-декорация» (ось 14) → вход этапа 2.

## Рамки

- Бюджет итерации: ≤3 кандидата, ~15 диспатчей; каденция R12.
- Красный канон на старте → итерация сначала чинит канон (или
  останавливается отчётом) — улучшения поверх красного не сажаются.
- Параллельная живая сессия: owns-конфликт → петля уступает (R4.d).
- Каждая итерация — свой DAG docs/tasks/YYYY-MM-DD_harness-evolution-
  loop-N.md (носитель хода) + стандартные журнальные события.
- Ярус: посадка механизмов требует полного Lead (D-0056-проверка на
  входе итерации); ниже привязки — итерация ограничивается этапами
  1-2 и очередью (матрица Role≠tier).

## Детекторы самой петли (R10(в))

Еженедельная калибровка разбирает итерации окна (DAG-файлы петли —
материал разбора `calibrated`): пропуск >2 дней при живом
расписании, серия пустых итераций при живых находках калибровки,
посадка мимо критик-гейта — находки О ПЕТЛЕ. Осевой блок и
провенанс — коммит посадки этого протокола.
